对 `$ARGUMENTS` 这个功能做参考调研，判据在 `rule://reference-first`。

## 派发

放在**同一个 `task` 批次**里并行派出三个 `reference-scout`，一仓一个——
不要派一个 agent 串着读三个仓，那会读不完也读不深。

每个 task 里必须写清：

- 要调研的功能是什么、ZCode 侧准备落在哪个 crate；
- **只读这一个仓**（给出绝对路径），另外两仓由同批次的兄弟负责；
- 从 `rule://reference-first` 的线索表里摘出与本主题相关的行作为起点；
- 输出按 `reference-scout` 定义的单仓六节报告；跨仓对照表由你汇总时拼，scout 不做跨仓比较。

三仓之外若本主题明显还有更合适的公开实现，可以额外派一个 `librarian` 去读该库源码，
但**不替代**三仓调研。

## 第一步：并表（你自己做，不要转述）

1. 把三份单仓报告并成一张对照表；结论冲突时**自己去读代码定论**，写出定论依据。
2. 常量阈值逐个标注成立前提；前提未知的显式标出。
3. 列出不能抄的部分及理由（上游已知债、平台特例）。

**到此为止不要选型。** 并表只陈述事实，裁决在闸门之后。

## 第二步：产品走向闸门

对照表出来后先分类。命中下列任一即为**产品走向级**：

- 改变用户可见行为或核心交互（渲染形态、命令语义、默认开关）；
- 改变数据模型或持久化格式（会话结构、落盘布局、迁移代价）；
- 改变权限与安全边界（审批粒度、沙箱、凭据存放）；
- 改变发布形态（二进制数量、平台矩阵、默认 feature 的体积代价）；
- 与 `rule://zcode-architecture` 或 `plans/tui/` 的既定决策冲突。

命中就**停下来问用户**：整理 2–4 个选项，每个写清**功能代价与性能代价**，标出你的推荐及理由。
**答复前不裁决、不实现。** 未命中的部分继续往下走，不要因为一处产品级分叉就把整件事挂起。

## 第三步：裁决与实施

1. 逐项裁决：抄哪家、怎么混、为什么。只说"综合考虑"不算裁决；实现细节按性能优先定。
2. 产品级项目按用户答复执行，不重新讨论。
3. 把移植方案的边界条件清单写进 todo 再开工——边界条件是移植时最容易整批丢掉的东西。
4. 前提未知的常量，要么补齐前提，要么在代码注释里写明"待验证"及验证方式。

调研不要停在报告：闸门放行的部分当轮进入实现。
