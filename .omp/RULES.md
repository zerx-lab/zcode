# ZCode 红线

- 未经用户明确要求，绝不 `git commit` / `git push` / 建 PR / 建 issue / 在 GitHub 上发表任何评论。
- 未经用户明确要求，绝不动 crates.io 上的已发布状态：`cargo publish` / `cargo owner` / `cargo yank`
  一律先问。发布走 `rule://zcode-workflow` 的发布入口，不手动替代。
- 会丢工作成果的命令先说明再执行：`git reset --hard`、`git clean -fd`、`git push --force`。
  先讲清会丢什么、有没有可恢复路径，拿到答复再动手。
- 绝不手改生成物。改生成器源头，见 `rule://zcode-architecture`。
- 绝不用占位实现冒充完成：stub、mock、`todo!()`、静默 fallback，以及 "MVP / v1 / 后续补" 式标签一律不算交付。
  做不到就直说缺哪个前置条件，并把能做完的部分做完。
- 非平凡实现（新子系统 / 新工具 / 并发与取消 / 缓存与截断 / 常量阈值 / 选依赖）动手前，
  必须先按 `rule://reference-first` 调研 oh-my-pi、jcode、opencode 三个参考仓的对应实现（`/ref <主题>`）。
  交付时写出对照结论（各家落点 `路径:行号` 与取舍理由），或明确"三仓均无，自研理由如下"。凭空发明按缺陷处理。
- 调研结论若会改变产品走向（用户可见行为、核心交互、数据模型、权限与安全边界、发布形态），
  先把选项与各自代价摆给用户，**拿到答复前不裁决、不实现**。纯实现细节自己按性能优先定，不要来回请示。
- 说 "已验证" 之前必须真的跑过对应路径，并写出跑了什么、看到什么。跑不了就说跑不了，不要用推测替代。
- 库代码里的 `unwrap` / `expect` / `panic!` 与 `as` 数值转换按缺陷处理；确属例外时同行写出理由。
- 新增约定前先搜现有实现。与既有约定并行的第二套写法一律拒绝：先迁移调用点，再删旧路径。
- 改动导出符号前必须用 `lsp references` 核实全部调用点，不靠猜、不靠文本搜索。
- 面向用户的散文与最终回答用简体中文；代码、命令、标识符保持英文。
